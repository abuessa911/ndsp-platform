## 0. الغرض من هذا الكتالوج

هذا الكتالوج هو المرجع التشغيلي الذي يحدد كيف تُبنى منظومة NDSP من الفكرة إلى التشغيل والصيانة. الغرض منه منع العشوائية، منع تكرار الصفحات، منع كسر التصميم، منع كشف أسرار المنظومة، وتوحيد طريقة العمل بين المالك والمطورين وأدوات الذكاء الاصطناعي.

أي تعديل أو تطوير أو ربط جديد داخل NDSP يجب أن يرجع إلى هذا الكتالوج قبل التنفيذ. لا يُعامل الكود وحده كمرجع نهائي. المرجع النهائي هو: **الهوية + الخريطة + الحوكمة + العقود البرمجية + الاختبارات + تقرير التعديل**.

## 1. تعريف النظام

NDSP ليست منصة توصيات بيع وشراء مباشرة، وليست مجرد صفحة أسعار، وليست لوحة رسومية فقط. NDSP هي منظومة دعم قرار تعتمد على طبقات تحليلية ومحركات داخلية لإنتاج قراءة منظمة لحالة السوق، السيناريو، المخاطر، جودة القرار، وحالة المتابعة.

المنظومة تهدف إلى تحويل التحليل المعقد إلى مخرجات مفهومة للمستخدم دون كشف الأسرار الداخلية أو تقديم أوامر تنفيذ مالية مباشرة.

### 1.1 صياغة التعريف المختصر

NDSP — Nawaf Decision Support Platform هي منصة دعم قرار تعرض قراءة حوكَمية لحالة السوق عبر محركات داخلية، مستويات سيناريو، طبقات مخاطر، وسياق زمني، مع إخراج نهائي يوضح حالة المتابعة وجودة القرار دون إصدار توصية مالية مباشرة.

### 1.2 المبادئ الحاكمة

1. القرار لا يخرج كأمر شراء أو بيع.
2. الواجهة تعرض قيمة مفهومة لا تفاصيل سرية.
3. كل صفحة لها غرض واضح ومصدر بيانات واضح.
4. كل API له عقد واضح.
5. كل تعديل له نسخة احتياطية وتقرير رجوع.
6. كل محرك قرار له مدخلات ومخرجات واختبار.
7. لا يتم تكديس سكربتات فوق سكربتات بلا حوكمة.
8. لا يتم تغيير أسماء الصفحات الرسمية عشوائياً.
9. لا يتم كشف الطبقات المحمية أو تفاصيل الحسابات الحساسة.
10. التشغيل الحقيقي أهم من الشكل، لكن الشكل يجب أن يخدم الثقة والفخامة والوضوح.

## 3. هوية المنتج

### 3.1 الاسم الرسمي

NDSP — Nawaf Decision Support Platform

### 3.2 وصف الهوية

هوية NDSP يجب أن تكون مؤسسية، داكنة، فخمة، قريبة من بيئة Bloomberg وTrading Terminal، لكن أكثر وضوحاً للمستخدم العادي. اللون الأساسي أسود داكن، واللون الثانوي ذهبي، مع تدرجات محايدة للحدود والبطاقات.

### 3.3 النبرة النصية

- واضحة.
- حازمة.
- غير مبالغ فيها.
- لا تستخدم وعود ربح.

## 4. خريطة المستخدم

### 4.1 رحلة الزائر

زائر → صفحة الهبوط → فهم القيمة → مشاهدة المنهجية العامة → قراءة إخلاء المسؤولية المختصر → التسجيل للتجربة → تأكيد الحساب → دخول البوابة.

### 4.2 رحلة المستخدم التجريبي

مستخدم تجريبي → قبول إخلاء المسؤولية → اختيار أصل → مشاهدة قراءة مبسطة → متابعة حالة السيناريو → استخدام مركز القرار → تجربة التنبيهات → ترقية اختيارية.

### 4.3 رحلة المستخدم المتقدم

مستخدم متقدم → تفعيل الوضع المتقدم → مشاهدة تفاصيل أوسع → مقارنة أصول → قراءة يوميات القرار → ضبط التنبيهات → متابعة جودة القرار.

### 4.4 رحلة المدير

Admin → تسجيل دخول آمن → مراجعة المستخدمين → مراجعة السجلات → مراقبة أخطاء النظام → مراجعة حالة API → إدارة التنبيهات العامة.

### 4.5 رحلة المالك

Owner → صلاحيات كاملة → مراجعة الحوكمة → Manual Override عند الحاجة → اعتماد الإصدارات → اعتماد كشف أو إخفاء بعض المخرجات → مراجعة السجلات الحساسة.

## 5. خريطة الصفحات

### 5.1 الصفحة الرئيسية Landing

**المسار المقترح:** `/` أو `/index.html`  
**الغرض:** بيع الفكرة وإظهار قيمة NDSP دون تعقيد.  
**المستخدم:** الزائر والمستخدم الجديد.

#### تعرض

- اسم NDSP.
- تعريف مختصر.
- القيمة الأساسية.
- المنهجية العامة.
- التجربة 16 يوم.
- الباقات.
- إخلاء مسؤولية مختصر.
- زر التسجيل.
- زر الدخول.
- شريط مؤشرات أو ملخص سوق إن وجد.

#### لا تعرض

- أسرار المحركات.
- أوامر بيع/شراء.
- تفاصيل الطبقات المحمية.

#### قبول الصفحة

- يجب أن تكون عربية بالكامل في النسخة العربية.
- يجب أن تكون متجاوبة للجوال.
- يجب ألا تحتوي أزرار مكررة بلا داعٍ.
- يجب أن تحمل هوية NDSP الداكنة والذهبية.

---

### 5.2 صفحة التسجيل

**الغرض:** إنشاء حساب مستخدم وتجربة 16 يوم.  
**المدخلات:** الاسم، البريد، الجوال، كلمة المرور.  
**القواعد:** منع تكرار البريد والجوال، تشفير كلمة المرور، قبول الشروط.

#### حالات الخطأ

- البريد مستخدم.
- الجوال مستخدم.
- كلمة المرور ضعيفة.
- صيغة البريد غير صحيحة.
- فشل الاتصال بالخادم.

---

### 5.3 صفحة الدخول

**الغرض:** مصادقة المستخدم.  
**القواعد:** منع رسائل تكشف وجود الحساب بشكل خطير، حماية من المحاولات المتكررة، جلسة آمنة.

#### تعرض

- البريد أو الجوال.
- كلمة المرور.
- زر الدخول.
- رابط نسيت كلمة المرور.

---

### 5.4 صفحة إخلاء المسؤولية

**الغرض:** منع دخول المنصة قبل تأكيد فهم المستخدم لطبيعة النظام.

#### نص الحوكمة

NDSP منصة دعم قرار وتحليل، وليست منصة توصيات مالية مباشرة. جميع المخرجات المعروضة هي قراءات تحليلية ومؤشرات متابعة، ولا تمثل أمراً بالشراء أو البيع أو الاحتفاظ. يتحمل المستخدم مسؤولية قراراته المالية ويجب عليه طلب استشارة مختص عند الحاجة.

#### القاعدة

لا يدخل المستخدم البوابة حتى يقبل الإخلاء.

---

### 5.5 بوابة المستخدم Dashboard

**الغرض:** تقديم ملخص سريع لحساب المستخدم وحالة القراءات.  
**تعرض:** حالة التجربة، الأصول المفضلة، آخر قراءة، التنبيهات، جودة النظام، اختصارات الصفحات.

- الأصفر = حذر أو تحت متابعة.

## 8. خريطة API

### 8.1 قواعد عامة

كل API يجب أن يحتوي على:

- مسار واضح.
- نوع الطلب.
- المدخلات.
- المخرجات.
- الأخطاء.
- الصلاحيات.
- الصفحات التي تستخدمه.
- اختبار قبول.

### 8.2 عقود API أساسية

#### تسجيل مستخدم

```txt
POST /api/auth/register
```

**المدخلات:** الاسم، البريد، الجوال، كلمة المرور.  
**المخرجات:** user_id، trial_ends_at، token أو رسالة تأكيد.  
**الأخطاء:** بريد مكرر، جوال مكرر، كلمة مرور ضعيفة.

#### تسجيل الدخول

```txt
POST /api/auth/login
```

**المدخلات:** البريد/الجوال، كلمة المرور.  
**المخرجات:** token، user profile، role.  
**الأخطاء:** بيانات غير صحيحة، حساب موقوف، محاولات كثيرة.

#### قراءة القرار الحية

```txt
GET /api/decision/quality-live?symbol=ETHUSDT
```

**المخرجات المطلوبة:**

```json
{
  "symbol": "ETHUSDT",
  "live_price": 0,
  "decision_quality": 0,
  "scenario_state": "UNDER_MONITORING",
  "directional_context": "NEUTRAL",
  "market_state": "RANGING",
  "reading_horizon": "WATCH",
  "horizon_strength": 0,
  "caution_reason": "Data under review",
  "scenario_levels": {
    "activation": 0,
    "arrival": 0,
    "review": 0,
    "invalidation": 0
  },
  "disclaimer": "Decision support only. Not financial advice."
}
```

#### حالة الخدمات

```txt
GET /api/health
```

**المخرجات:** حالة API، قاعدة البيانات، مزود الأسعار، محركات القرار، آخر تحديث.

## 10. خريطة محركات القرار

### 10.1 ترتيب المحركات

```txt
TDL
→ Market Direction
→ Scenario Levels
→ NMP
→ Momentum
→ Macro USD
→ Risk
→ Devil’s Advocate
→ Decision Quality
→ Final State
```

### 10.2 TDL Engine

**الغرض:** تحديد السياق الزمني والمنطقي للقرار.  
**يعرض اسمه؟** نعم.  
**يحجب؟** لا يحجب وحده إلا إذا البيانات غير صالحة أو غير محدثة.  
**المدخلات:** بيانات COT، الأصل، الإطار الزمني، التصنيف.  
**المخرجات:** سياق زمني، تحيز أولي، حالة متابعة.

### 10.3 NMP Engine

**الغرض:** تحديد منطقة التقاء حرجة دون كشف آلية الحساب الدقيقة.  
**يعرض اسمه؟** نعم.  
**يحجب؟** لا، لكنه مطلوب للانتقال إلى بعض حالات التأكيد الآلي.  
**المخرجات:** حالة قرب/بعد، منطقة مرجعية مخفية أو مبسطة.

### 10.4 Market Direction Engine

**الغرض:** تحديد الاتجاه العام أو حالة الحياد.  
**يعرض اسمه؟** لا يلزم، يمكن عرض النتيجة فقط.  
**المخرجات:** bullish, bearish, neutral, mixed.

### 10.5 Scenario Levels Engine

**الغرض:** إنتاج مستويات السيناريو: التفعيل، الوصول، المراجعة، الإلغاء.  
**يعرض؟** نعم، كقيم مستخدم مفهومة.  
**القيد:** لا تعرض مستويات وهمية؛ إن لم تتوفر البيانات تعرض “قيد التحقق”.

### 10.6 Momentum Engine

**الغرض:** قياس قوة الحركة والتعارضات.  
**يعرض؟** النتيجة فقط، لا تفاصيل كاملة.

### 10.7 Macro USD Engine

**الغرض:** قراءة ضغط أو دعم الدولار للأصول العكسية.  
**الموقع في السلسلة:** قبل Risk وDevil’s Advocate.  
**يعرض؟** كدعم/ضغط/محايد.

### 10.8 Risk Engine

**الغرض:** تقييم المخاطر قبل الاعتراض النهائي.  
**يعرض؟** نعم، بلغة بسيطة.  
**الألوان:** أخضر، أصفر، أحمر.

### 10.9 Devil’s Advocate Layer

**الغرض:** اختبار القرار ضد الاعتراضات والمخاطر.  
**الصلاحية:** الطبقة الوحيدة التي تملك حق الحجب النهائي.  
**يعرض اسمها؟** نعم باسم “طبقة محامي الشيطان”.  
**تعرض للمستخدم:** نتيجة الاعتراض العامة وسبب حذر مختصر.  
**لا تعرض:** تفاصيل القواعد الحساسة.

### 10.10 Decision Quality Engine

**الغرض:** تحويل نتائج الطبقات إلى درجة جودة قرار.  
**المخرجات:** score من 0 إلى 100، مستوى ثقة، حالة جودة.

### 10.11 Final State Engine

**الغرض:** إخراج الحالة النهائية.  
**الحالات:**

```txt
UNDER_MONITORING
CAUTION
ALLOWED_WITH_CAUTION
BLOCKED
DATA_NOT_READY
```

## 11. خريطة الحوكمة

### 11.1 قواعد التعديل

1. أي تعديل يبدأ بنسخة احتياطية.
2. أي تعديل ينتهي بتقرير.
3. لا تعديل على أكثر من نطاق إلا إذا كان مخططاً.
4. لا إصلاح عشوائي من خلال لصق سكربتات كثيرة.
5. عند فشل تعديل، يتم الرجوع لا ترقيع الخلل فوق الخلل.
6. لا يتم حذف صفحة رسمية دون إذن Owner.
7. لا يتم تغيير اسم صفحة في القائمة إلا بتحديث الخريطة.
8. كل API جديد يوثق.
9. كل حقل جديد في JSON يوثق.
10. كل محرك جديد يضاف إلى خريطة المحركات.

### 11.2 قواعد العرض والإخفاء

- تظهر فقط الأسماء المسموحة للمستخدم.
- الطبقات المحمية تعرض كحالة أو جودة لا كاسم داخلي.
- تفاصيل الحسابات الحساسة لا تعرض.
- واجهة المستخدم لا تعرض مخرجات raw debug.
- رسائل الأخطاء لا تكشف مفاتيح أو مسارات داخلية حساسة.

### 11.3 قواعد القرار

- NDSP لا يوصي بالشراء أو البيع.
- المخرجات دعم قرار فقط.
- محامي الشيطان هو طبقة الحجب النهائية.
- لا يتم اعتبار القرار نهائياً إذا البيانات غير محدثة.
- إذا فشل مزود بيانات مهم، تعرض الحالة DATA_NOT_READY أو UNDER_MONITORING.

## 23. الخلاصة التنفيذية

هذا الكتالوج هو صمام أمان NDSP. المشروع لا يحتاج فقط إلى كود؛ يحتاج إلى خريطة تمنع الفوضى. كل صفحة يجب أن تعرف دورها، كل API يجب أن يعرف عقده، كل محرك يجب أن يعرف مكانه، وكل تعديل يجب أن يترك أثراً موثقاً.

إذا تم الالتزام بهذا الكتالوج، تتحول NDSP من مجموعة صفحات وترقيعات إلى منظومة قابلة للبناء والتطوير والتسويق والصيانة.
