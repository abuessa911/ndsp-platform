# NDSP Final Pre-Implementation Transition Plan
## خطة الانتقال النهائي قبل بدء التطبيق

**المشروع:** NDSP — Nawaf Decision Support Platform  
**الإصدار:** v1.0  
**التاريخ:** 2026-07-06  
**الغرض:** تحويل الحزم السابقة من ملفات نظرية إلى نظام عمل داخل المشروع، ثم بدء التطبيق الفعلي بطريقة آمنة ومنظمة.

---

# 1. خلاصة الوضع الحالي

تم تجهيز الحزم الأساسية التالية:

```txt
1. System Build & Readiness Catalog
   كتالوج بناء وتجهيز النظام

2. Build Tools & Control Pack
   حزمة أدوات التحكم والبناء

3. Execution Ready Pack
   حزمة الجاهزية التنفيذية
```

هذه الحزم تعني أن المشروع لم يعد يحتاج إلى مزيد من الكلام العام.  
المرحلة التالية هي إدخال هذه الحزم داخل المشروع، تشغيل الفحص، تثبيت الواقع الحالي، ثم البدء بالتنفيذ مرحلة مرحلة.

---

# 2. هل بقي شيء قبل التطبيق؟

نعم، بقيت خطوات انتقالية قليلة لكنها حاسمة:

```txt
1. تثبيت كل الملفات داخل الريبو/المشروع.
2. تشغيل فحص السيرفر والمشروع.
3. تعبئة القيم الحقيقية للمسارات والخدمات.
4. تجميد نطاق V1.
5. تحويل الخطة إلى مهام تنفيذية.
6. تجهيز اختبار بسيط قبل كل نشر.
7. اعتماد إخلاء المسؤولية النهائي.
8. بدء التنفيذ بعد نجاح الفحص والنسخ الاحتياطي.
```

بعد هذه الخطوات، يبدأ التطبيق الفعلي.

---

# 3. قاعدة مهمة

لا يبدأ أي تعديل برمجي جديد قبل تنفيذ الآتي:

```txt
1. رفع/نسخ ملفات الوثائق إلى داخل المشروع.
2. تشغيل Audit Script.
3. قراءة تقرير الفحص.
4. تثبيت المسارات والخدمات الحقيقية.
5. تشغيل Backup Script.
6. تنفيذ تعديل صغير ومحدد.
7. تشغيل Post Patch Test.
```

أي أداة ذكاء اصطناعي أو مطور يتجاوز هذه الخطوات يعتبر يعمل خارج الحوكمة.

---

# 4. مكان وضع الملفات داخل المشروع

يجب وضع الحزم داخل مجلد `docs` ومجلد `scripts` بهذا الشكل:

```txt
ndsp/
├── docs/
│   ├── 00-build-catalog/
│   ├── 01-build-control-pack/
│   ├── 02-execution-ready-pack/
│   ├── 03-final-transition/
│   ├── 04-legal/
│   └── 05-runbooks/
├── scripts/
│   ├── audit/
│   ├── backup/
│   ├── tests/
│   └── deploy/
├── frontend/
├── backend/
├── .env.example
└── README.md
```

إذا كان المشروع الحالي له هيكل مختلف، لا يتم إعادة بنائه من الصفر.  
يتم فقط إنشاء مجلدات الوثائق والسكريبتات داخله بدون كسر الموجود.

---

# 7. أمر فحص الوضع الحالي

يجب تشغيل سكربت الفحص الموجود في حزمة الجاهزية التنفيذية:

```bash
chmod +x scripts/audit/ndsp_server_and_project_audit_AR.sh
FRONTEND_DIR="/var/www/ndsp-my" \
BACKEND_DIR="$HOME/empire-core-new" \
FRONTEND_BASE="https://my.ndsp.app" \
API_BASE="https://api.ndsp.app" \
scripts/audit/ndsp_server_and_project_audit_AR.sh
```

إذا كانت المسارات مختلفة، يجب تعديل المتغيرات فقط، وليس تعديل السكربت مباشرة.

---

# 8. أمر النسخ الاحتياطي قبل أول تعديل

```bash
chmod +x scripts/backup/ndsp_safe_backup_before_patch_AR.sh
FRONTEND_DIR="/var/www/ndsp-my" \
BACKEND_DIR="$HOME/empire-core-new" \
scripts/backup/ndsp_safe_backup_before_patch_AR.sh
```

لا يتم تنفيذ أي تعديل بدون تقرير Backup واضح.

---

# 9. أمر اختبار ما بعد التعديل

```bash
chmod +x scripts/tests/ndsp_post_patch_test_AR.sh
FRONTEND_DIR="/var/www/ndsp-my" \
FRONTEND_BASE="https://my.ndsp.app" \
API_BASE="https://api.ndsp.app" \
scripts/tests/ndsp_post_patch_test_AR.sh
```

إذا فشل الاختبار، لا يتم نشر التعديل ولا يتم البناء فوقه.  
يجب إصلاح السبب أو الرجوع للنسخة الاحتياطية.

# 12. إعداد اختبار ونشر بسيط

في البداية لا نحتاج CI/CD معقد.  
نحتاج فحص بسيط قبل أي نشر:

```txt
1. npm build إن وجدت واجهة Node/Next/Vite.
2. اختبار Python/FastAPI إن وجد.
3. فحص صفحات HTTP 200.
4. فحص API القرار.
5. فحص الرادار والقائمة.
6. فحص عدم وجود Buy/Sell.
7. فحص SSL وNginx.
```

يمكن لاحقاً تحويل هذه الخطوات إلى GitHub Actions.

# 14. إخلاء المسؤولية النهائي

يجب إنشاء ملف:

```txt
docs/04-legal/NDSP_LEGAL_DISCLAIMER_MASTER_AR.md
```

ويجب أن يتضمن:

```txt
- NDSP منصة دعم قرار فقط.
- ليست توصية مالية.
- لا تقدم أوامر شراء أو بيع.
- لا تضمن أرباحاً أو نتائج.
- البيانات قد تتأخر أو تنقطع.
- المستخدم مسؤول عن قراراته.
- القراءات تحليلية وتعليمية ومساندة فقط.
```

ولا يسمح بدخول المستخدم للبوابة قبل قبول هذا الإخلاء.

---

# 15. أمر الأداة الذكية لتنفيذ هذه المرحلة

انسخ هذا النص لأي أداة بناء:

```txt
أنت تعمل على مشروع NDSP.
المطلوب الآن ليس بناء ميزة جديدة، بل تنفيذ مرحلة الانتقال النهائي قبل التطبيق.

نفذ الآتي فقط:
1. ضع ملفات الحزم داخل docs و scripts حسب الهيكل المحدد.
2. لا تعدل الواجهة أو الباك إند الآن.
3. شغل Audit Script أو جهز أمر تشغيله إذا لم تملك صلاحية التنفيذ.
4. استخرج المسارات والخدمات الحقيقية من التقرير.
5. أنشئ ملف V1_FREEZE.md.
6. أنشئ Backlog أولي بالمهام.
7. جهز مسار Backup وPost Patch Test.
8. لا تبدأ أي تعديل برمجي قبل نجاح الفحص والنسخ الاحتياطي.

ممنوع:
- حذف صفحات.
- تغيير تصميم.
- تعديل API.
- كشف محركات سرية.
- إضافة Buy/Sell.
- بناء شيء جديد قبل انتهاء مرحلة الفحص.
```

# 17. أول تعديل مقترح بعد الجاهزية

بعد اكتمال هذه الوثيقة وتشغيل الفحص، أول تعديل لا يكون كبيراً.  
الأفضل أن يكون:

```txt
تثبيت إخلاء المسؤولية + التأكد من أن الصفحات الرسمية لا تفقد القائمة والرادار.
```

لأن هذا تعديل مهم، واضح، وقابل للاختبار.

---

# 18. الخلاصة النهائية

نعم، بعد هذه الوثيقة غالباً لا يبقى شيء تأسيسي مهم.  
المرحلة التالية ليست المزيد من المستندات، بل التطبيق العملي بهذا الترتيب:

```txt
1. إدخال الوثائق داخل المشروع.
2. تشغيل الفحص.
3. تثبيت الواقع الحالي.
4. النسخ الاحتياطي.
5. تنفيذ أول تعديل.
6. اختبار ما بعد التعديل.
7. التكرار مرحلة مرحلة حتى اكتمال V1.
```

هذه هي نقطة الانتقال من التخطيط إلى التنفيذ.
