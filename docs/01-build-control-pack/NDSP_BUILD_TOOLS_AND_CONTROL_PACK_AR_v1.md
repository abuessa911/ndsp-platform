# حزمة أدوات وضبط بناء نظام NDSP

**اسم المستند:** NDSP Build Tools & Control Pack  
**المشروع:** NDSP — Nawaf Decision Support Platform  
**المالك:** Nawaf  
**نوع النظام:** منصة دعم قرار وليست منصة توصيات تداول أو تنفيذ صفقات  
**الإصدار:** v1.0  
**الغرض:** تحديد الأدوات والمستندات والحوكمة اللازمة لبناء النظام بشكل صحيح وسليم ومنع التخبيص أثناء التطوير أو النشر أو الصيانة.

---

## 1. الهدف من هذه الحزمة

هذه الحزمة ليست قائمة أدوات عشوائية. الهدف منها هو إنشاء **خط إنتاج منظم** لبناء نظام NDSP، بحيث لا تعمل أي أداة ذكاء اصطناعي أو مبرمج أو سكربت بطريقة عشوائية.

المسار الصحيح لبناء النظام هو:

```txt
توثيق → تصميم → تنفيذ → اختبار → نشر → مراقبة → صيانة
```

أي بناء بدون هذه السلسلة قد يؤدي إلى:

- كسر صفحات موجودة.
- اختفاء الرادار أو القائمة الجانبية.
- تكرار الصفحات أو تغيير أسمائها.
- كشف أسماء محركات داخلية يجب إخفاؤها.
- تعديل الباك إند بدون داعٍ.
- ربط واجهات بحقول API غير صحيحة.
- تكديس سكربتات فوق سكربتات.
- صعوبة الرجوع للإصدار السابق.

---

## 2. القاعدة الأساسية للبناء

الأداة وحدها لا تبني نظاماً صحيحاً.  
الترتيب الصحيح هو:

```txt
كتالوج النظام + الحوكمة + خريطة الصفحات + عقد API + خطة اختبار + خطة نشر + سكربت فحص
```

بعدها فقط يتم السماح لأدوات مثل Codex أو Cursor أو أي أداة بناء أخرى بالتعديل.

## 4. وثيقة الحوكمة الرئيسية

**اسم الملف المقترح:**

```txt
NDSP_MASTER_GOVERNANCE_RULES.md
```

### الغرض

هذه الوثيقة هي دستور المشروع. أي أداة أو مبرمج يعمل على NDSP يجب أن يلتزم بها قبل لمس الكود.

### القواعد الأساسية

- NDSP منصة دعم قرار وليست منصة تنفيذ تداول.
- لا يتم عرض توصيات مباشرة مثل Buy أو Sell.
- لا يتم كشف أسماء المحركات الداخلية السرية.
- لا يتم تعديل الباك إند إلا عند الحاجة الواضحة.
- لا يتم تكديس سكربتات أو تكرار حلول فوق حلول سابقة.
- كل تعديل يجب أن يسبقه Backup.
- كل تعديل يجب أن ينتج عنه تقرير واضح.
- لا يتم تغيير أسماء الصفحات الرسمية عشوائياً.
- لا يتم حذف القائمة الجانبية أو الرادار أو إخلاء المسؤولية.
- كل صفحة يجب أن يكون لها مصدر بيانات معروف.
- كل API يجب أن يكون له عقد واضح.
- أي تغيير في التصميم لا يجوز أن يكسر الوظائف الحالية.

### قاعدة مهمة خاصة بـ NDSP

طبقة **محامي الشيطان** هي الطبقة الوحيدة التي تملك حق الحجب النهائي داخل منطق القرار. بقية الطبقات تساعد أو تحذر أو تقيم، لكنها لا تحجب إلا إذا نصت الحوكمة على ذلك.

## 5. سجل الصفحات الرسمي

**اسم الملف المقترح:**

```txt
NDSP_PAGE_REGISTRY.md
```

### الغرض

منع تكرار الصفحات أو تغيير أسمائها أو اختفاء الروابط أثناء التعديل.

### الصفحات الأساسية المقترحة

```txt
/index.html
صفحة الهبوط الرئيسية

/decision-support.html
صفحة دعم القرار

/NDSP_Asset_View.html
صفحة عرض الأصل

/NDSP_Command_Center.html
مركز القرار

/NDSP_Daily_Brief.html
يوميات القرار

/NDSP_Settings_Alerts.html
الإعدادات والتنبيهات

/admin
لوحة الإدارة
```

### قواعد الصفحات

- لا يتم تغيير اسم صفحة رسمية إلا بقرار واضح.
- لا يتم إنشاء نسخة مكررة من صفحة موجودة.
- لا يتم حذف صفحة من القائمة الجانبية بدون توثيق.
- كل صفحة يجب أن تحتوي على غرض واضح.
- كل صفحة مربوطة ببيانات يجب أن تذكر مصدر API الخاص بها.

## 6. عقد API الرسمي

**اسم الملف المقترح:**

```txt
NDSP_API_CONTRACT.md
```

### الغرض

تثبيت طريقة التواصل بين الواجهة والباك إند ومنع التخمين في أسماء الحقول.

### مثال Endpoint مهم

```txt
GET /api/decision/quality-live?symbol=ETHUSDT
```

### المدخلات

```json
{
  "symbol": "ETHUSDT"
}
```

### المخرجات المتوقعة

```json
{
  "live_price": 0,
  "decision_quality": 0,
  "scenario_state": "UNDER_MONITORING",
  "directional_context": "NEUTRAL",
  "market_state": "UNKNOWN",
  "reading_horizon": "PENDING",
  "horizon_strength": "PENDING",
  "caution_reason": "Data under processing",
  "sanitized_summary": "Decision support reading only. Not financial advice."
}
```

### الصفحات التي تستخدم هذا API

```txt
decision-support.html
NDSP_Asset_View.html
NDSP_Command_Center.html
NDSP_Daily_Brief.html
```

### قواعد API

- لا تعتمد الواجهة على حقل غير موثق.
- لا يتم تغيير اسم حقل إلا مع تحديث العقد.
- إذا تعطل مزود البيانات يجب أن يرجع API حالة واضحة وليس صفحة مكسورة.
- لا يظهر للمستخدم أي خطأ تقني خام.

## 12. خطة الرجوع للإصدار السابق

**اسم الملف المقترح:**

```txt
NDSP_ROLLBACK_PLAN.md
```

### الغرض

ضمان إمكانية الرجوع إذا تسبب التعديل في كسر الصفحة أو API أو التصميم.

### يجب أن تحتوي على

- أين توجد النسخ الاحتياطية.
- كيف يتم استرجاع الواجهة.
- كيف يتم استرجاع إعدادات Nginx.
- كيف يتم استرجاع service files.
- كيف يتم إيقاف النسخة الجديدة.
- كيف يتم التأكد أن النسخة القديمة تعمل.

### قاعدة ذهبية

أي سكربت تعديل لا يحتوي على rollback أو backup يعتبر غير آمن للإنتاج.

## 20. الخلاصة التنفيذية

الأداة الأنسب لبناء NDSP ليست أداة واحدة. التركيبة الصحيحة هي:

```txt
GitHub للحفظ والإصدارات
Codex CLI للتنفيذ
ChatGPT للتخطيط والحوكمة والسكريبتات
Cursor للمراجعة والتحرير
Figma/Canva للتصميم فقط
curl/pytest/Playwright للاختبار
Nginx/systemd/PM2 للنشر
Uptime Kuma/Sentry/Netdata للمراقبة
```

لكن قبل استخدام أي أداة تنفيذ، يجب تجهيز:

```txt
NDSP_BUILD_CONTROL_PACK
```

هذه الحزمة هي التي تحمي المشروع من العبث، وتحول البناء من محاولات عشوائية إلى نظام واضح قابل للتطوير والصيانة.
