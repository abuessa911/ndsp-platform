# حوكمة التحول الآمن وبناء الثبات أولًا لمنظومة NDSP

**الاسم الرسمي:** NDSP — Nawaf Decision Support Platform  
**معرّف الوثيقة:** `NDSP-STABILITY-GOV-001`  
**الإصدار:** `1.0.0`  
**تاريخ الاعتماد:** `2026-07-11`  
**المالك وصاحب القرار النهائي:** Nawaf  
**الحالة:** `GOVERNING / ملزمة`  
**النطاق:** المصدر، الإنتاج، الخدمات، البيانات، العقود، الأمن، سجل القرار، المختبر التاريخي، والطبقات المستقبلية.

---

## 1. الغرض من الوثيقة

هذه الوثيقة هي المرجع الحاكم لترتيب العمل على NDSP بعد تدقيق الواقع الحالي. هدفها منع التوسع العشوائي، حماية النظام الحي، وتوجيه كل جهد نحو زيادة الثبات وقابلية التدقيق والاستعادة والتطوير التجاري والعلمي.

لا تُعد هذه الوثيقة وصفًا نظريًا؛ بل **قانون عمل** لكل تعديل أو بناء أو تنظيف أو نشر داخل NDSP.

---

## 2. هوية NDSP وحدود المنتج

NDSP هي **منظومة دعم قرار** وليست منصة تنفيذ صفقات، ولا بوت تداول، ولا خدمة توصيات مباشرة.

القواعد الثابتة:

1. المحركات الحتمية تحسب القرار.
2. الذكاء الاصطناعي يشرح القرار ولا يملكه.
3. الأخبار توفر السياق ولا تملك اتجاه القرار.
4. NDSP Bot يستهلك القرارات المكتملة فقط عبر بوابة تكامل خارجية.
5. لا يسمح لأي واجهة أو بوت أو طبقة نصية بتجاوز حوكمة القرار.
6. لا تُكشف المعادلات الخاصة أو الأسرار التشغيلية أو مسارات الإدارة الداخلية للمستخدم العام.

---

## 3. القانون الأعلى

> **من الآن فصاعدًا، كل نقطة جهد يجب أن تزيد الثبات، لا التعقيد.**

ويُترجم هذا القانون إلى القواعد التالية:

- لا إضافة لطبقة جديدة قبل حماية الواقع الحالي.
- لا تعديل على الإنتاج قبل نسخة احتياطية واختبار تراجع.
- لا اعتماد على نسخة احتياطية لم يُختبر استرجاعها.
- لا حذف لخدمة أو ملف أو إصدار قبل إثبات أنه غير مستخدم.
- لا تعديل مباشر على ملفات النشر الحية إلا في حالة طوارئ موثقة.
- لا تغيير في عقد JSON دون رقم إصدار وخطة توافق.
- لا تغيير في محرك قرار داخل تعديل واجهة.
- لا توسع عالمي قبل ثبات النظام وإثبات قيمة المنتج.

## 4. ترتيب التحول الإلزامي

لا يجوز تغيير هذا الترتيب إلا بقرار مالك موثق.

### المرحلة 0 — تجميد آمن وتثبيت الواقع

المخرجات الإلزامية:

- `NDSP_CURRENT_PRODUCTION_REALITY_LOCK`
- خريطة المصدر الحاكم.
- خريطة النطاقات وNginx.
- سجل الخدمات والمنافذ والمستخدمين.
- سجل قواعد البيانات والمخازن.
- سجل مسارات `/home` و`/opt` و`/var/www` و`/etc`.
- قائمة ما يُمنع لمسه مؤقتًا.
- قائمة مخاطر P0 وP1 وP2.

**بوابة الخروج:** لا توجد معلومة أساسية مجهولة عن مصدر الإنتاج أو الخدمة المسؤولة عن كل نطاق.

---

### المرحلة 1 — نسخة احتياطية كاملة واختبار استعادة

المخرجات الإلزامية:

- `NDSP_PRE_CHANGE_FULL_BACKUP`
- `NDSP_BACKUP_MANIFEST`
- `NDSP_SECRETS_ENCRYPTED_BACKUP`
- نسخ متناسقة لقواعد البيانات.
- نسخة ملفات المصدر وGit.
- نسخة `/opt` التشغيلية.
- نسخة `/var/www`.
- نسخة Nginx وsystemd وPM2 وCron وDocker.
- `SHA256SUMS`
- `RESTORE_INSTRUCTIONS`
- `NDSP_FULL_RESTORE_VERIFICATION_OK`

قواعد النسخ:

1. ثلاث نسخ، على وسيطين، ونسخة واحدة خارج الخادم.
2. الأسرار تحفظ في حزمة مشفرة منفصلة.
3. لا تُنقل بيانات المستخدمين أو الأسرار إلى المحادثات.
4. اختبار الاستعادة يتم في مسار أو بيئة معزولة.
5. لا يُقبل نجاح النسخ دون إثبات استعادة عملي.

**بوابة الخروج:** استعادة ناجحة موثقة للمصدر والإعدادات وقاعدة البيانات وعينة تشغيل غير إنتاجية.

---

### المرحلة 2 — تثبيت المصدر الحاكم

المخرجات الإلزامية:

- `NDSP_CANONICAL_SOURCE_LOCK`
- تحديد المستودع الرسمي والفرع الإنتاجي.
- تحديد المسار المصدر الحقيقي لكل تطبيق.
- تحديد مسار Build ومسار Deploy.
- ربط كل خدمة بملف مصدر داخل Git.
- منع `rsync --delete` من مصدر غير متحقق.
- توثيق Git commit لكل إصدار.
- منع التعديل اليدوي على `dist` أو `/var/www` إلا بطوارئ موثقة.

قانون المصدر:

```text
SOURCE → BUILD → VALIDATE → PREVIEW/STAGING → APPROVE → DEPLOY → VERIFY
```

ولا يُقبل المسار العكسي:

```text
EDIT LIVE FILES → TRY TO REMEMBER LATER
```

**بوابة الخروج:** يمكن إعادة بناء النسخة الحية من Commit معروف وبأمر موثق.

---

### المرحلة 3 — تنظيف الخدمات والنسخ المتكررة

المخرجات الإلزامية:

- `NDSP_SERVICE_REGISTRY`
- `NDSP_PORT_REGISTRY`
- `NDSP_DEPENDENCY_MAP`
- تصنيف كل خدمة: حاكمة، مساندة، قديمة، مرشحة للإيقاف، أو مجهولة.
- تحديد المستهلكين الفعليين لكل بوابة ومنفذ.
- دمج المسؤوليات المتكررة تدريجيًا.
- نقل الخدمات المهمة من `/opt` إلى مصدر محكوم أو توثيقها رسميًا.
- تقليل الخدمات ذات صلاحية root.
- إزالة النسخ القديمة فقط بعد فترة مراقبة وخطة رجوع.

قاعدة الحذف:

> لا حذف بناءً على الاسم أو العمر. الحذف يتطلب إثبات عدم وجود مستهلك، نسخة احتياطية، فترة تعطيل تجريبية، وخطة رجوع.

**بوابة الخروج:** لكل خدمة مالك، مصدر، منفذ، مستخدم تشغيل، Health Check، مستهلكون، وخطة تراجع.

---

### المرحلة 4 — حماية الأسرار والمنافذ

المخرجات الإلزامية:

- `NDSP_SECURITY_AND_SECRETS_GOVERNANCE`
- تدوير كلمات مرور قواعد البيانات وJWT وSMTP والمفاتيح الإدارية.
- فحص Git history للأسرار القديمة.
- نقل الأسرار خارج المصدر.
- تقييد PostgreSQL وRedis وواجهات الإدارة على Localhost أو شبكة خاصة.
- مراجعة XRDP وSSH وSMTP.
- تطبيق Firewall موثق.
- Rate limiting وحماية محاولات الدخول.
- فصل حسابات الخدمة ومبدأ أقل صلاحية.
- حماية `/data/` والملفات الداخلية من العرض العام.
- توقيع Webhooks واستخدام Idempotency للعمليات الحساسة.

**بوابة الخروج:** لا يوجد سر داخل المصدر، ولا منفذ حساس مكشوف بلا مبرر واعتماد.

---

### المرحلة 5 — توحيد العقود والسجلات

المخرجات الإلزامية:

- `NDSP_DATA_AND_DECISION_CONTRACT_GOVERNANCE`
- سجل موحد لكل JSON Schema.
- نسخة عقد صريحة: `contract_version`.
- توحيد معرفات الأصول والرموز.
- توحيد أكواد الحالة والأخطاء.
- OpenAPI لواجهات REST.
- AsyncAPI أو CloudEvents للأحداث.
- تنسيق سجل موحد يتضمن:
  - `timestamp`
  - `service`
  - `environment`
  - `trace_id`
  - `request_id`
  - `decision_id`
  - `asset_id`
  - `contract_version`
  - `engine_version`
  - `error_code`
- سياسة Deprecation وتوافق خلفي.
- منع العقود المكررة أو المتعارضة.

**بوابة الخروج:** كل منتج أو خدمة يستهلك عقدًا معروفًا ومختبرًا وقابلًا للتحقق آليًا.

---

### المرحلة 6 — إنشاء سجل أدلة القرار

المخرج الحاكم:

- `NDSP_DECISION_EVIDENCE_LEDGER`

يجب أن يحفظ لكل قرار:

- معرف القرار.
- الأصل والفريم والزمن.
- Snapshot لكل مدخل.
- مصادر البيانات وتوقيت الجلب.
- نسخ TDL وNMP والزخم والمخاطر ومحامي الشيطان.
- تاريخ انتقال الحالة:
  - `BLOCKED`
  - `ALLOWED`
  - `ARMED`
  - `EXECUTED` عند التطبيق المصرح به فقط.
- أسباب الانتقال أو الإلغاء.
- مستويات التفعيل والوصول والمراجعة والإلغاء.
- استخدام Manual Override إن حدث.
- بصمة السجل وGit commit.
- سجل Append-only؛ لا تُعدل الحقيقة القديمة.

قاعدة السجل:

> عند تغير القرار يُضاف حدث جديد، ولا يُعاد كتابة القرار القديم.

**بوابة الخروج:** يمكن تفسير أي قرار وإثبات مدخلاته ونسخ محركاته كما كانت وقت صدوره.

### المرحلة 7 — مختبر الإعادة التاريخية

المخرج الحاكم:

- `NDSP_HISTORICAL_REPLAY_LAB`

الشروط:

- استخدام البيانات المتاحة في الزمن الأصلي فقط.
- منع الشموع غير المغلقة.
- منع البيانات الاقتصادية المعدلة لاحقًا.
- منع الأخبار التي لم تكن منشورة وقت القرار.
- استخدام نسخة المحرك الفعلية لذلك التاريخ.
- اكتشاف `FUTURE_LEAKAGE`.
- مقارنة Strict وAdaptive.
- تقييم الاتجاه والجاهزية والثقة والمخاطر والتوقيت.

الحالات:

```text
REPLAY_EXACT
REPLAY_APPROXIMATE
REPLAY_INCOMPLETE
FUTURE_LEAKAGE_DETECTED
SOURCE_SNAPSHOT_MISSING
```

**بوابة الخروج:** إعادة إنتاج مجموعة قرارات تاريخية بنتائج قابلة للمقارنة وبدون تسرب مستقبلي.

## 6. تصنيف التغييرات

### P0 — طارئ حرج

أمثلة: كشف سر، حذف بيانات، اختراق، توقف شامل، فساد قاعدة بيانات.

- يسمح باختصار الدورة فقط لحماية النظام.
- يجب أخذ Snapshot سريع إن أمكن.
- يجب توثيق ما حدث خلال 24 ساعة.
- يجب إنشاء تقرير سبب جذري.

### P1 — حرج غير طارئ

أمثلة: منفذ حساس مكشوف، خدمة متعارضة، عقد مصادقة غير محمي، خطر نشر قد يمسح ملفات.

- لا ينفذ دون Backup وRollback واختبار.
- يعالج قبل الميزات الجديدة.

### P2 — تحسين أساسي

أمثلة: توحيد العقود، تحسين المراقبة، خفض الصلاحيات، تنظيم السجلات.

- يدخل في Sprint محكوم.
- لا يُخلط مع إصلاح P0/P1 في نفس النشر.

### P3 — ميزة أو تحسين تجربة

أمثلة: صفحة جديدة، تصميم، لغة، تقرير إضافي.

- يؤجل إذا لم تُغلق مخاطر P0/P1 المتعلقة به.

## 7. ما يُمنع حاليًا

حتى نجاح النسخة والاستعادة وقفل المصدر:

- تشغيل سكربت نشر يستخدم `--delete`.
- حذف أو تعطيل بوابة أو خدمة بناءً على تشابه الاسم.
- تعديل مباشر في `/var/www`.
- تغيير TDL أو NMP داخل إصلاح واجهة.
- فتح منافذ جديدة.
- إدخال أسرار في Git أو المحادثات.
- حذف Backups قديمة قبل فهرستها.
- دمج خدمات `/opt` قبل تحديد المستهلكين.
- إعادة بناء المصادقة دون Migration واختبار توافق.
- إضافة طبقات أخبار أو AI إلى القرار الحاكم.
- تسويق عالمي مدفوع واسع قبل ثبات النظام والامتثال.

## 8. حوكمة المحركات والقرار

1. لكل محرك:
   - مالك.
   - إصدار.
   - مدخلات.
   - مخرجات.
   - اختبارات.
   - Commit.
   - تاريخ تفعيل.
   - نسخة رجوع.
2. لا دخول بدون Correction وفق السياسة المعتمدة.
3. NMP إلزامي للتنفيذ الآلي واختياري للـManual Override المملوك للمالك.
4. المخاطر وUSD Macro يسبقان محامي الشيطان.
5. القوة لا تساوي الجاهزية.
6. الاتجاه لا يساوي الثقة.
7. لا يظهر للمستخدم العام إلا ما تسمح به مصفوفة الرؤية.
8. لا يصدر NDSP تعليمات تنفيذ مباشرة من طبقة نصية أو خبرية.

## 9. حوكمة الواجهة والتجربة

- Beginner هو الوضع الافتراضي.
- Professional يعرض التفاصيل دون كشف الملكية الفكرية.
- Admin يدير التشغيل المصرح به.
- Owner يملك التعديلات الجوهرية وManual Override.
- القائمة الجانبية هي المرجع الملاحي.
- لا تكرار للأقسام في الرأس والقائمة.
- العربية والإنجليزية والفرنسية تستخدم مفاتيح ترجمة موحدة.
- لا نصوص ثابتة داخل المكونات الجديدة.
- كل صفحة لها Owner وRoute وData Contract وAcceptance Test.
- التصميم لا يغير القرار أو العقد.

- نجاح طلبات المزودين.
- زمن الاستجابة.
- البيانات القديمة أو المفقودة.
- فشل العقود.

- استخدام Fallback.
- أخطاء المصادقة.

### التتبع

```text
REQUEST
→ ASSET RESOLUTION
→ DATA SOURCE
→ QUALITY GATE
→ TDL
→ NMP
→ RISK
→ CONTEXT
→ GOVERNANCE
→ RESPONSE
```

### التنبيهات

- P0: فوري.
- P1: خلال نافذة تشغيل قصيرة.
- P2: تقرير يومي أو أسبوعي.
- لا تنبيه دون `error_code` و`service` و`trace_id`.

- انخفاض الخدمات المكررة.
- انخفاض العمليات بصلاحية root.
- صفر أسرار داخل المصدر.
- صفر منافذ حساسة مكشوفة بلا اعتماد.
- جميع العقود ذات نسخ ومخططات.
- كل قرار قابل للتتبع.
- نجاح الإعادة التاريخية دون تسرب.
- انخفاض أعطال النشر.
- ارتفاع ثبات المستخدمين ومعدل الاحتفاظ.
- إمكانية إعادة بناء الإنتاج من المصدر الموثق.

```text
CANONICAL_SOURCE = LOCKED
P0_RISKS = CLOSED
SERVICE_REGISTRY = COMPLETE
SECRETS = ROTATED_AND_EXTERNALIZED
CONTRACTS = VERSIONED
OBSERVABILITY = ACTIVE
DECISION_LEDGER = OPERATIONAL
```

## 16. النص المثبت في صفحة عمل المشروع

> **NDSP تعمل وفق مبدأ الثبات أولًا. ترتيب العمل الملزم هو: نسخة احتياطية كاملة واختبار استعادة، تثبيت المصدر الحاكم، تنظيف الخدمات والنسخ المتكررة، حماية الأسرار والمنافذ، توحيد العقود والسجلات، إنشاء سجل أدلة القرار، إنشاء مختبر الإعادة التاريخية، ثم إضافة طبقات البيانات والأخبار والتفسير. لا تعديل على الإنتاج دون Backup وTest وRollback واعتماد وتحقق بعد النشر. لا نحذف أو ندمج أي خدمة قبل إثبات عدم وجود مستهلك. كل جهد جديد يجب أن يزيد الثبات وقابلية التدقيق، لا التعقيد.**
